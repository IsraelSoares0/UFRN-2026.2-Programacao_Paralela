\section{Introdução}

A atividade consiste em simular o movimento de um fluido em 2D com a equação de
Navier--Stokes, considerando apenas a viscosidade (sem pressão e sem forças
externas), e depois paralelizar o código com OpenMP. O objetivo principal é
observar como o \textbf{particionamento dos dados} entre as threads e o
\textbf{balanceamento de carga}, controlados pelas cláusulas \texttt{schedule} e
\texttt{collapse}, afetam o desempenho. A medição foi feita com o PaScal Suite.

\section{Paralelização com OpenMP}

\subsection{Particionamento de dados e balanceamento de carga}

O trabalho do programa é aplicar o mesmo cálculo a cada ponto de uma malha
$1024 \times 1024$, a cada passo de tempo. Paralelizar significa dividir esses
pontos entre as threads. Foram avaliadas duas formas de dividir:

\begin{itemize}
    \item \textbf{\texttt{schedule(static)}}: o laço externo (as linhas da malha)
    é dividido em blocos contíguos de mesmo tamanho, um por thread, definidos
    antes da execução. Com 8 threads, cada uma recebe 128 das 1024 linhas.
    \item \textbf{\texttt{collapse(2)}}: os dois laços (linhas e colunas) são
    tratados como um único conjunto de $1024^2$ pontos, e esse conjunto é dividido
    entre as threads, também de forma estática. Com 8 threads, cada uma recebe
    131.072 pontos.
\end{itemize}

\begin{table}[ht]
\centering
\caption{Como cada versão divide o trabalho entre as threads.}
\label{tab:particao}
\small
\begin{tabular}{l p{4.6cm} r r}
\toprule
Versão & O que é dividido & Unidades & Por thread (8 threads) \\
\midrule
\texttt{schedule(static)} & linhas da malha & 1.024 & 128 linhas \\
\texttt{collapse(2)} & pontos da malha & 1.048.576 & 131.072 pontos \\
\bottomrule
\end{tabular}
\end{table}

\paragraph{Balanceamento de carga.} Todos os pontos exigem o mesmo trabalho, e
1024 é divisível por 2, 4 e 8. Por isso, as duas versões distribuem o trabalho
de forma igual entre as threads em todas as configurações testadas, e não
existe desbalanceamento a corrigir. Esse é o cenário em que o escalonamento
estático é indicado. As políticas \texttt{dynamic} e \texttt{guided}, que
entregam pedaços de trabalho às threads durante a execução, são úteis quando o
custo de cada iteração varia, o que não ocorre aqui.

\paragraph{O que o \texttt{collapse} muda no código.} Para fundir os laços, o
cálculo dos vizinhos periódicos das linhas (\texttt{im} e \texttt{ip}) precisou
ser movido para dentro do laço interno, e passa a ser refeito a cada ponto
(Apêndice~\ref{ap:codigo}). A versão com \texttt{collapse} divide o trabalho em
partes menores, mas executa mais instruções por ponto.

\subsection{Configuração do experimento}

A malha foi fixada em $1024 \times 1024$, e o único parâmetro de entrada foi o
tempo final simulado. As entradas i1 a i4 dobram o tempo simulado a cada passo,
de modo que o trabalho total também dobra. O PaScal Analyzer foi usado com
instrumentação manual da região do passo de tempo, para 1, 2, 4 e 8 cores.

\subsection{Diferenças de desempenho}

\paragraph{Pelo speedup e pela eficiência, o \texttt{collapse} parece melhor.}
Com 2, 4 e 8 cores, o \texttt{collapse} tem speedup maior e eficiência maior
(Tabela~\ref{tab:medias}). Com 2 cores, a eficiência média é de 95,9\%, contra
71,4\% do \texttt{static}.

\paragraph{Mas esses indicadores usam bases diferentes.} Com 1 core, o
\texttt{collapse} leva em média 44\% mais tempo que o \texttt{static} (na maior
entrada, 8,379~s contra 5,878~s). Como o speedup compara cada versão com o
próprio tempo com 1 core, o \texttt{collapse} parte de uma base mais lenta, o
que melhora seus indicadores. Para comparar de forma justa, a
Tabela~\ref{tab:comum} mostra o tempo do \texttt{collapse} em relação ao do
\texttt{static}, e o speedup das duas versões usando o 1 core do
\texttt{static} como referência.

\paragraph{Em tempo absoluto, o \texttt{static} é equivalente ou melhor.}
\begin{itemize}
    \item Com 2 cores, o \texttt{collapse} é cerca de 7\% mais lento.
    \item Com 4 cores, os tempos são praticamente iguais (o \texttt{collapse} é
    cerca de 3\% mais rápido, até 7,7\% na maior entrada). Os tempos não trazem
    desvio padrão, então uma diferença desse tamanho pode ser variação entre
    execuções.
    \item Com 8 cores, o \texttt{collapse} é cerca de 12\% mais lento. Em todas
    as entradas, o menor tempo é o do \texttt{static} com 8 cores.
\end{itemize}

\paragraph{Ganho ao passar de 4 para 8 cores.} O \texttt{static} reduz o tempo
em 16\% a 20\%, enquanto o \texttt{collapse} reduz apenas 2\% a 7\%. Nas duas
versões, a eficiência com 8 cores é baixa (35,8\% e 46,1\%)

\paragraph{Sobre o balanceamento.} Como as duas versões já dividem o trabalho
de forma igual entre as threads, a diferença de desempenho não vem do
balanceamento de carga. Dividir o trabalho em partes menores, como faz o
\texttt{collapse}, não trouxe ganho neste problema, e a versão com
\texttt{collapse} executa mais instruções por ponto.

\section{Conclusão}

\begin{itemize}
    \item A simulação teve o comportamento esperado: o fluido parado permaneceu
    parado, e a perturbação se espalhou suavemente, de acordo com a solução
    analítica.
    \item Como a carga é uniforme e a malha é divisível pelo número de threads,
    o escalonamento estático já balanceia a carga, e o \texttt{schedule(static)}
    no laço externo foi suficiente.
    \item O \texttt{collapse(2)} aparenta escalar melhor no PaScal Viewer, mas
    isso se deve em boa parte ao seu tempo com 1 core ser 44\% maior.
    \item Em tempo absoluto, o \texttt{schedule(static)} é equivalente ou
    melhor, e dá o menor tempo com 8 cores (1,980~s contra 2,145~s na maior
    entrada).
    \item Speedup e eficiência relativos ao próprio 1 core devem ser lidos junto
    com os tempos absolutos antes de se escolher uma cláusula.
\end{itemize}

\section{Código-fonte dos kernels}
\label{ap:codigo}

Os trechos a seguir são o passo de tempo das duas versões avaliadas. A
compilação foi feita com \texttt{gcc -O2 -Wall -fopenmp ... -lm -lmpascalops}.

\begin{lstlisting}[style=cstyle, caption={Versão \texttt{schedule}: paralelismo apenas no laço externo}, label={lst:sched}]
#define IDX(i, j, N) ((i) * (N) + (j))

static void passo(const double *u, const double *v,
                  double *un, double *vn, int N, double r)
{
    pascal_start(1);
    #pragma omp parallel for schedule(runtime)
    for (int i = 0; i < N; i++) {
        int im = (i == 0)     ? N - 1 : i - 1;
        int ip = (i == N - 1) ? 0     : i + 1;
        for (int j = 0; j < N; j++) {
            int jm = (j == 0)     ? N - 1 : j - 1;
            int jp = (j == N - 1) ? 0     : j + 1;

            double lap_u = u[IDX(ip, j, N)] + u[IDX(im, j, N)]
                         + u[IDX(i, jp, N)] + u[IDX(i, jm, N)]
                         - 4.0 * u[IDX(i, j, N)];
            double lap_v = v[IDX(ip, j, N)] + v[IDX(im, j, N)]
                         + v[IDX(i, jp, N)] + v[IDX(i, jm, N)]
                         - 4.0 * v[IDX(i, j, N)];

            un[IDX(i, j, N)] = u[IDX(i, j, N)] + r * lap_u;
            vn[IDX(i, j, N)] = v[IDX(i, j, N)] + r * lap_v;
        }
    }
    pascal_stop(1);
}
\end{lstlisting}

\begin{lstlisting}[style=cstyle, caption={Versão \texttt{collapse}: laços \texttt{i} e \texttt{j} fundidos}, label={lst:coll}]
static void passo(const double *u, const double *v,
                  double *un, double *vn, int N, double r)
{
    pascal_start(1);
    #pragma omp parallel for collapse(2) schedule(static)
    for (int i = 0; i < N; i++) {
        for (int j = 0; j < N; j++) {
            int im = (i == 0)     ? N - 1 : i - 1;
            int ip = (i == N - 1) ? 0     : i + 1;
            int jm = (j == 0)     ? N - 1 : j - 1;
            int jp = (j == N - 1) ? 0     : j + 1;

            double lap_u = u[IDX(ip, j, N)] + u[IDX(im, j, N)]
                         + u[IDX(i, jp, N)] + u[IDX(i, jm, N)]
                         - 4.0 * u[IDX(i, j, N)];
            double lap_v = v[IDX(ip, j, N)] + v[IDX(im, j, N)]
                         + v[IDX(i, jp, N)] + v[IDX(i, jm, N)]
                         - 4.0 * v[IDX(i, j, N)];

            un[IDX(i, j, N)] = u[IDX(i, j, N)] + r * lap_u;
            vn[IDX(i, j, N)] = v[IDX(i, j, N)] + r * lap_v;
        }
    }
    pascal_stop(1);
}
\end{lstlisting}
